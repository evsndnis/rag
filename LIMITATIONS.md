# Слабые стороны и пути доработки

Это учебный проект, на котором разбирается весь RAG-пайплайн. Нагрузочных тестов и защиты приватных данных в нём нет, а доступ к LLM упирается в лимиты провайдера. Если запускать такой сервис в компании, эти части придётся доработать.

Ниже разобраны пять областей: качество поиска, нагрузка, приватность данных, время до первого токена и полнота корпуса. Для каждой описано, в чём проблема и как её проверить или устранить.

## 1. Качество поиска

**Что сейчас.** Поиск идёт по векторам: `multilingual-e5-small` (118 МБ) → косинусная близость в Qdrant → top-4 чанка → LLM. Чанки нарезаны по 1000 символов с перекрытием 200. На golden dataset из 10 вопросов: Recall@4 = 1.00, Faithfulness = 0.86, Response Relevancy = 0.94 (см. [README](README.md#метрики)).

**Где сломается.** На вопросах из двух частей («объясни Ridge и покажи разницу с Lasso»), на запросах с точными именами («что вернёт `LogisticRegression.predict_proba`» — эмбеддер плохо ловит сигнатуры методов) и на вопросах с числами («сколько типов кросс-валидации в sklearn»). На таких вопросах Recall падает, и вместо ответа получается общий рассказ про линейные модели.

**Куда расти** (от простого к сложному):

- **Гибридный поиск (hybrid search).** Поиск по словам (BM25) объединяется с поиском по эмбеддингам, результаты сводятся через Reciprocal Rank Fusion. Так находятся точные имена и обозначения. В LangChain: `EnsembleRetriever([bm25, dense], weights=[0.5, 0.5])`.
- **Reranker** — ✅ *уже реализован, включается через `RERANK_ENABLED=true`*. Из top-20 чанков cross-encoder `ms-marco-MiniLM-L-6-v2` (~80–90 МБ) отбирает лучшие, оценивая каждую пару «запрос — чанк» по отдельности. На нашем прогоне Faithfulness выросла с 0.86 до 0.90, цена — примерно +200 мс на запрос. Осталось решить, включать ли его по умолчанию.
- **Расширение запроса (query expansion).** LLM формулирует 3–5 вариантов вопроса, поиск идёт по всем. Стоит одного дополнительного LLM-вызова и помогает на коротких и размытых вопросах.
- **Большой эмбеддер** — `bge-m3` или `multilingual-e5-large` (1.3 ГБ) вместо `-small`. Recall вырастет, но на VPS с 2 ГБ модель уже не поместится: понадобится 4+ ГБ RAM или отдельный сервер эмбеддингов.

Доработку выбирайте по найденным ошибкам и после каждого изменения прогоняйте тот же golden dataset. Важна не только итоговая метрика, но и объяснение, почему выбран именно такой retriever.

## 2. Нагрузка и масштабирование

**Что сейчас.** Один процесс uvicorn и один контейнер Qdrant на общей VPS. Эмбеддер создаётся при старте приложения. Ограничения частоты запросов и отдельной очереди задач нет, цепочка вызывается синхронно.

**Где сломается.** Уже при нескольких одновременных пользователях uvicorn блокируется на синхронном `chain.invoke()` (LLM отвечает 5–10 секунд), и следующий запрос ждёт в очереди. При десятках одновременных запросов nginx начнёт отдавать `502 Bad Gateway`, не дождавшись ответа, а потом закончится память.

**Куда расти:**

- **Несколько воркеров uvicorn** — `uvicorn app.main:app --workers 4`. Каждый воркер — отдельный процесс со своей копией эмбеддера, поэтому память растёт кратно числу воркеров. На VPS с 2 ГБ это не поместится, нужно 4+ ГБ.
- **Асинхронный поиск** — `await retriever.ainvoke()` вместо `.invoke()`: пока Qdrant отвечает по сети, event loop обслуживает другие запросы. Сам расчёт эмбеддинга в sentence-transformers останется синхронным.
- **Шлюз к LLM с очередью.** Между сервисом и OpenRouter ставится LiteLLM или очередь на Redis с rate limiting. Под большой нагрузкой первым заканчивается лимит провайдера, и шлюз вернёт пользователю честный `429` вместо таймаута.
- **Горизонтальное масштабирование.** Несколько копий rag-app за балансировщиком (nginx или HAProxy), общие Qdrant и Redis для кэша. Запросы распределяются между копиями, а общие данные хранятся отдельно.
- **CDN для статики.** Gradio при первом открытии отдаёт несколько мегабайт JS и CSS. Если раздавать их через CDN (у Cloudflare есть бесплатный тариф), VPS разгрузится.

Главный вопрос здесь: какую часть сервиса масштабировать первой и какими замерами подтвердить этот выбор.

## 3. Приватность данных

**Что сейчас.** Корпус — публичная документация scikit-learn. Запросы пользователя идут в OpenRouter, а оттуда к провайдеру выбранной модели. Сторонний провайдер видит каждый вопрос и весь найденный контекст, то есть чанки, которые попадают в промпт. Сколько он хранит логи и учится ли на них, зависит от его условий.

**Где это критично:**

- **В корпусе персональные данные клиентов** (ФИО, email, телефоны, паспорта). 152-ФЗ запрещает передавать их третьим лицам без согласия, а каждый `/chat`-запрос отправляет в OpenRouter фрагмент с такими данными.
- **В корпусе коммерческая тайна** (внутренние ТЗ, исходники, финансовые отчёты). Провайдер может обучить на ней модель, и кусок вашего ТЗ всплывёт в ответе другому клиенту.
- **Чувствительны сами вопросы.** Для медицинского справочника поток запросов «симптомы X, диагноз Y» — это данные о здоровье.

**Минимальная гигиена даже для учебного проекта:**

- В `data/local/` и `data/corpus_chunks.jsonl` не кладите ничего, что нельзя выложить в публичный репозиторий. Если для тренировки индексировали внутренние документы, после теста удалите коллекцию из Qdrant.
- Не пишите в логи полный текст вопроса. Для диагностики хватит длины вопроса или его хэша.

**Куда расти, если корпус действительно чувствительный:**

- **Локальная LLM** — llama-3.3-70b через vLLM или Ollama на своём GPU-сервере, тогда запросы не уходят за периметр компании. Дорого по железу, и нужен инженер на поддержку.
- **Локальные эмбеддинги** у нас уже есть: sentence-transformers считает их в контейнере сервиса. Но найденный текст всё равно уходит во внешнюю LLM, так что без локальной модели данные компанию покидают.
- **Фильтр персональных данных на входе** — проверка вопроса до `chain.invoke()`. Presidio или набор регулярных выражений найдёт в вопросе, например, email клиента и отклонит запрос. Содержимое найденных документов такая проверка не смотрит.
- **Корпоративный тариф LLM-провайдера.** У OpenAI, Anthropic и OpenRouter есть тарифы с договором об обработке данных и гарантией, что на ваших запросах не обучают модели. Это вариант для компаний с большими расходами на LLM, небольшой команде проще поднять локальную модель.

**Качество ответов** в учебной версии тоже упрощено: модель может выдумать адрес источника, смешать языки или выдать правдоподобное утверждение, которого нет в чанках. Именно это и ловит Faithfulness: у нас 0.86 (0.90 с reranker), а рабочему сервису нужно 0.95+. Помогают более строгий системный промпт («отвечай строго по контексту, если данных нет — I don't know») и проверка ответа перед отправкой пользователю (guardrails).

## 4. Время до первого токена

Стриминг даёт TTFT около 500 мс, и это дешёвая часть оптимизации. В крупных рабочих системах добавляют ещё несколько приёмов:

- **Упреждающий поиск.** Retrieval запускается по уже набранному тексту, пока пользователь дописывает вопрос. К моменту отправки чанки готовы, и LLM стартует сразу.
- **Кэш на уровне поиска.** Пары «эмбеддинг запроса → найденные чанки» хранятся, например, в Redis, и на повторных похожих запросах поиск не выполняется.
- **Прогрев моделей.** Периодические пустые запросы к LLM-провайдеру, чтобы первый запрос пользователя не попал на холодный старт модели (актуально для serverless).

При проверке интерфейса смотрите и на TTFT, и на полное время ответа: начало пользователь видит быстро, но остальной текст ему всё равно нужно дождаться.

## 5. Расширение корпуса

**Что сейчас.** Корпус состоит из трёх модулей scikit-learn (линейные модели, деревья решений и метрики) и `data/local/about.md`, всего ~265 чанков. Они покрывают большую часть вопросов по классическому ML, но не все темы. Про ансамбли, кросс-валидацию, препроцессинг и подбор гиперпараметров сервис отвечает плохо или честно говорит, что данных нет.

### Шаг 1. Добавить модули в `SEED_URLS`

В [`app/scripts/load_corpus.py`](app/scripts/load_corpus.py) расширьте список:

```python
SEED_URLS = [
    # Default trio
    "https://scikit-learn.org/stable/modules/linear_model.html",
    "https://scikit-learn.org/stable/modules/tree.html",
    "https://scikit-learn.org/stable/modules/model_evaluation.html",
    # Extension
    "https://scikit-learn.org/stable/modules/ensemble.html",
    "https://scikit-learn.org/stable/modules/cross_validation.html",
    "https://scikit-learn.org/stable/modules/preprocessing.html",
    "https://scikit-learn.org/stable/modules/compose.html",
    "https://scikit-learn.org/stable/modules/grid_search.html",
    "https://scikit-learn.org/stable/modules/impute.html",
    "https://scikit-learn.org/stable/modules/feature_selection.html",
]
```

С 10 модулями корпус вырастет примерно с 270 до 560 чанков: около 2 МБ данных в Qdrant и около 10 МБ дополнительной памяти при поиске. Индексация требует больше памяти, чем поиск по готовому индексу, поэтому на VPS с 2 ГБ её нужно запускать отдельно от приложения.

### Шаг 2. Обновить `about.md`

Добавьте новые темы в [`data/local/about.md`](data/local/about.md) и переиндексируйте корпус. Иначе на вопрос «что ты умеешь» сервис ответит по старому описанию.

Заодно обновите Recall@4 в [`notebooks/rag_eval.ipynb`](notebooks/rag_eval.ipynb): сейчас он считается по совпадению раздела `linear_model` / `tree` / `model_evaluation` в URL.

### Шаг 3. Переиндексировать с остановленным app

```bash
ssh root@<vps-ip>
cd /opt/mentoring/rag-service
git pull
docker compose stop app
docker compose run --rm app sh -c \
  "python -m app.scripts.load_corpus && python -m app.scripts.index_corpus"
docker compose start app
```

Индексация ~560 чанков занимает несколько минут, и всё это время приложение недоступно.

> **Важно:** перед индексацией 10 модулей вместо 3 проверьте, что на VPS настроен swap на 2 ГБ. Он даёт запас памяти, но останавливать приложение на время индексации всё равно нужно.

### Шаг 4. Проверить новые темы

Задайте вопросы по новым модулям:

- `What is StratifiedKFold?`
- `Как использовать SimpleImputer?`
- `GridSearch или RandomizedSearch — что выбрать?`

Retriever должен находить фрагменты из соответствующих модулей, а ответы должны подтверждаться этими фрагментами. Вопросы стоит добавить в golden dataset и перепрогнать метрики.
