# Слабые стороны и пути доработки

Сервис покрывает весь RAG-пайплайн, но в нём нет нагрузочных тестов и защиты приватных данных, а доступ к LLM зависит от лимитов провайдера. Перед использованием в продакшене эти части нужно доработать.

Ниже разобраны пять областей: качество поиска, нагрузка, приватность данных, время ожидания ответа и расширение корпуса. Для каждой указаны возможная проблема и способы её проверить или устранить.

## 1. Качество поиска

**Что сейчас.** Поиск по векторам: `multilingual-e5-small` (118 МБ) → косинусная близость в Qdrant → top-4 чанка → LLM. Чанки по 1000 символов с перекрытием 200. На golden dataset из 10 вопросов: Recall@4 = 1.00, Faithfulness = 0.86, Response Relevancy = 0.94 (подробнее — в [README](README.md#метрики)).

**Где сломается.** На вопросах из двух частей («объясни Ridge и покажи разницу с Lasso»), на запросах с точными именами («что вернёт `LogisticRegression.predict_proba`» — эмбеддер плохо ловит сигнатуру метода) и на вопросах с числами («сколько типов кросс-валидации в sklearn»). Recall на таких вопросах падает, а ответы превращаются в общий рассказ про линейные модели. Кроме того, 10 вопросов — слишком маленький golden dataset, чтобы уверенно сравнивать варианты retriever'а.

**Куда расти** (в порядке возрастания сложности):

- **Гибридный поиск (hybrid search)** объединяет поиск по словам (BM25) и по эмбеддингам, а результаты сводит через Reciprocal Rank Fusion. Так находятся точные имена и обозначения. В LangChain это `EnsembleRetriever([bm25, dense], weights=[0.5, 0.5])`.
- **Reranker** уже реализован опционально (`RERANK_ENABLED=true`): cross-encoder `ms-marco-MiniLM-L-6-v2` отбирает top-5 из top-20 и поднимает Faithfulness с 0.86 до 0.90. По умолчанию выключен — стоит замерить задержку (ориентировочно +~200 мс на запрос) и решить, включать ли его в продакшене.
- **Расширение запроса (query expansion)** — LLM составляет 3–5 переформулировок вопроса, и поиск идёт по всем. Стоит один дополнительный LLM-вызов; помогает на коротких и неясных вопросах.
- **Большой эмбеддер** — `bge-m3` или `multilingual-e5-large` (1.3 ГБ) вместо `-small`. Recall вырастет, но на VPS с 2 ГБ модель уже не поместится: нужны 4+ ГБ RAM или отдельный сервер эмбеддингов.

Доработку выбирать по найденным ошибкам, а после каждого изменения прогонять тот же golden dataset ([notebooks/rag_eval.ipynb](notebooks/rag_eval.ipynb)).

## 2. Нагрузка и масштабирование

**Что сейчас.** Один процесс uvicorn и один контейнер Qdrant на общей VPS. Эмбеддер создаётся при старте приложения. В коде нет ограничения частоты запросов и отдельной очереди задач; вызовы цепочки выполняются синхронно.

**Где сломается.** Уже при нескольких одновременных пользователях uvicorn блокируется на синхронном `chain.invoke()` (LLM отвечает 5–10 секунд), и следующий запрос ждёт в очереди. При десятках одновременных запросов nginx начнёт отдавать `502 Bad Gateway`, не дождавшись ответа приложения, а дальше закончится память.

**Куда расти:**

- **Несколько воркеров uvicorn** — `uvicorn app.main:app --workers 4`. Каждый воркер — отдельный процесс со своей копией эмбеддера, поэтому память растёт кратно. На VPS с 2 ГБ не поместится, нужны 4+ ГБ.
- **Асинхронный поиск** — `await retriever.ainvoke()` вместо `.invoke()`: пока Qdrant отвечает по сети, цикл событий свободен для других запросов. Сам расчёт эмбеддинга в sentence-transformers остаётся синхронным.
- **Шлюз к LLM с очередью** — между сервисом и OpenRouter поставить LiteLLM или очередь на Redis с ограничением частоты. При большой нагрузке первым заканчивается лимит провайдера, и шлюз честно вернёт пользователю `429` вместо таймаута.
- **Горизонтальное масштабирование** — несколько копий rag-service за балансировщиком (nginx или HAProxy), общие Qdrant и Redis для кэша. Запросы распределяются между копиями приложения, а общие данные хранятся отдельно.
- **CDN для статики** — интерфейс Gradio отдаёт несколько мегабайт JS и CSS при каждом первом открытии. Если раздавать эти файлы через CDN (у Cloudflare есть бесплатный тариф), VPS разгрузится.

Прежде чем масштабировать, нужен нагрузочный тест (например, locust или k6): он покажет, какая часть сервиса упирается первой.

## 3. Приватность данных

**Что сейчас.** Корпус — публичная документация scikit-learn (scikit-learn.org). Запросы пользователя идут в OpenRouter, оттуда — к провайдеру выбранной модели. Сторонний провайдер видит каждый вопрос и весь найденный контекст — чанки, которые вставляются в промпт. Как долго он хранит логи и использует ли их для дообучения, зависит от его условий.

**Где это критично** — если тот же пайплайн применить к другому корпусу:

- Корпус содержит **персональные данные клиентов** (ФИО, email, телефоны, паспортные данные): закон 152-ФЗ запрещает передавать их третьим лицам без согласия, а каждый `/chat`-запрос отправляет фрагмент с такими данными в OpenRouter.
- Корпус содержит **коммерческую тайну** (внутренние ТЗ, исходники, финансовые отчёты): провайдер может обучить на них модель, и кусок ТЗ всплывёт в ответе другому клиенту.
- **Сами вопросы пользователей чувствительны**: у медицинского справочника поток запросов «симптомы X, диагноз Y» — это данные о здоровье.

**Минимальная гигиена:**

- В `data/local/` и `data/corpus_chunks.jsonl` не класть ничего, что нельзя положить в публичный репозиторий. Если для экспериментов проиндексированы внутренние документы — после теста удалить коллекцию из Qdrant.
- В логах сервиса не писать полный текст вопроса пользователя. Для диагностики достаточно длины вопроса или его хэша.

**Куда расти, если корпус действительно чувствительный:**

- **Локальная LLM** — поднять `llama-3.3-70b` через vLLM или Ollama на собственном GPU-сервере: запросы не уходят за периметр. Дорого по железу и требует поддержки.
- **Локальные эмбеддинги** уже есть: sentence-transformers считает их в контейнере сервиса. Но найденный текст всё равно уходит внешней LLM, так что без локальной модели обработка не останется внутри.
- **Фильтр персональных данных на входе** — проверка вопроса до `chain.invoke()`. Presidio или набор регулярных выражений найдёт email клиента в вопросе и отклонит запрос. Содержимое найденных документов такая проверка не смотрит.
- **Корпоративный тариф LLM-провайдера** — у OpenAI, Anthropic и OpenRouter есть тарифы с договором об обработке данных и гарантией не обучать модели на ваших запросах. Это путь при больших расходах на LLM; при небольших проще локальная модель.

**Качество ответов LLM.** Модель может выдумать адрес источника, смешать языки или написать правдоподобное, но не подтверждённое чанками утверждение. Это и измеряет Faithfulness: сейчас 0.86 (0.90 с reranker'ом), а для продакшена нужно 0.95+. Помогут более строгий системный промпт («ответ строго из контекста, если данных нет — I don't know») и проверка ответа перед отправкой пользователю (guardrails).

## 4. Время до первого токена

Стриминг даёт TTFT около 500 мс — это то, чего можно добиться дёшево. В крупных системах добавляют ещё несколько приёмов:

- **Упреждающий поиск** — пока пользователь дописывает вопрос, запускать retrieval по уже набранному тексту. К моменту отправки чанки готовы, и LLM стартует сразу.
- **Кэш на уровне поиска** — хранить пары «эмбеддинг запроса → найденные чанки», например в Redis. На повторных похожих запросах поиск не выполняется.
- **Прогрев моделей** — периодические пустые запросы к LLM-провайдеру, чтобы первый запрос пользователя не попал на холодный старт модели (актуально для serverless).

Смотреть стоит и на TTFT, и на полное время ответа: пользователь быстро видит начало, но ему ещё нужно дождаться остального текста.

## 5. Расширение корпуса

Корпус сейчас — три модуля scikit-learn: линейные модели, деревья решений и метрики (265 чанков вместе с `about.md`). Они покрывают большую часть типовых вопросов, но не весь классический ML: нет ансамблей, кросс-валидации, препроцессинга, подбора гиперпараметров.

### Шаг 1. Добавить модули в `SEED_URLS`

В [app/scripts/load_corpus.py](app/scripts/load_corpus.py):

```python
SEED_URLS = [
    # Текущие модули
    "https://scikit-learn.org/stable/modules/linear_model.html",
    "https://scikit-learn.org/stable/modules/tree.html",
    "https://scikit-learn.org/stable/modules/model_evaluation.html",
    # Расширение
    "https://scikit-learn.org/stable/modules/ensemble.html",
    "https://scikit-learn.org/stable/modules/cross_validation.html",
    "https://scikit-learn.org/stable/modules/preprocessing.html",
    "https://scikit-learn.org/stable/modules/compose.html",
    "https://scikit-learn.org/stable/modules/grid_search.html",
    "https://scikit-learn.org/stable/modules/impute.html",
    "https://scikit-learn.org/stable/modules/feature_selection.html",
]
```

Ожидаемый рост — с ~270 до ~560 чанков: ~2 МБ данных в Qdrant и ~10 МБ дополнительной памяти при поиске. Индексация требует больше памяти, чем готовый поиск, поэтому на VPS с 2 ГБ её нужно выполнять отдельно от приложения.

### Шаг 2. Обновить `about.md`

Добавить новые темы в `data/local/about.md`. Иначе на вопрос «что ты умеешь» сервис ответит по старому описанию.

### Шаг 3. Переиндексировать с остановленным приложением

`data/` не входит в Docker-образ, поэтому на сервере монтируем её из клона репозитория. Контейнер индексации подключается к той же сети `rag-net`, что и Qdrant:

```bash
ssh <user>@<vps-ip>
cd <path-to-repo> && git pull
docker stop rag-service
docker run --rm --network rag-net \
  -e LLM_API_KEY=<ключ> \
  -v "$PWD/data:/app/data" \
  ghcr.io/<owner>/rag-service:latest \
  sh -c "python -m app.scripts.load_corpus && python -m app.scripts.index_corpus"
docker start rag-service
```

Индексация ~560 чанков занимает несколько минут, и всё это время сервис недоступен. Перед запуском проверить, что на VPS включён swap (~2 ГБ): он даёт запас памяти, но не отменяет остановку приложения.

### Шаг 4. Проверить новые темы

- `What is StratifiedKFold?`
- `Как использовать SimpleImputer?`
- `GridSearch или RandomizedSearch — что выбрать?`

Retriever должен находить фрагменты из соответствующих модулей, а ответы — подтверждаться этими фрагментами. После расширения стоит дополнить golden dataset вопросами по новым модулям и заново прогнать метрики.
